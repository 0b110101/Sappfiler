### 0.1 冲突可行性结论

**可以做到，不存在"无法解决"的冲突。但"无缝"需要靠工程约束换，不是自动化就能保证的。**

实测证据（`git merge-tree --write-tree`，2026-10-03）：

| 场景 | 冲突文件 | 性质 |
|---|---|---|
| 现在：`main` ← `feature/multi-backend-sync` | **恰好 2 个**：`Directory.Build.props`、`src/Sappfiler.App/Package.appxmanifest` | 纯版本号，机械冲突（两边各自升过版）。22 个文件里其余 20 个**自动合并干净** |

**为什么版本号文件必然冲突**：这是**已经拍板的分支策略**（HANDOVER 0.2 规则 4）——两条分支各自维护自己的版本线（`0.3.2-alpha.x` / `0.4.0-alpha.x`），版本升位提交**故意不互相合并**。

### 0.2 真正的风险不是 git 冲突，而是这两条

**(A) 命名撞车：`feature` 分支已经占用了「Sync」这个词。**

| feature 已占用 | 本分支必须改用 | 原因 |
|---|---|---|
| `src/Sappfiler.Core/Models/SyncModels.cs` | `DeviceSyncModels.cs` | 同路径 → **add/add 冲突** |

**(B) 概念撞车（比 git 冲突严重）：`remote_mappings` 与 feature 的 `game_mappings` 是同一个东西的两套设计。**

**我的建议（需要你拍板）**：本分支**直接采用 feature 已定的 `game_mappings` 表名与列形状**（含 `provider` 列），不要另起 `remote_mappings`。这样将来两个分支在这一点上**自动合流**，而不是留两套。代价：本分支要"提前"引入 `game_mappings` 表——但它本来就要建表，等于免费。

## 1. 现有架构复核（CURRENT ARCHITECTURE）

> 依据：`main` @ `1df2042` 实际代码（新分支基线）。所有结论标注了文件与行号。

### 1.1 现有数据库（**main 是 6 张表，不是 feature 的 9 张**）

| 表 | 作用 | 关键约束 |
|---|---|---|
| `games` | 游戏身份（platform + platform_id） | `UNIQUE(platform, platform_id)` |
| `sessions` | 会话事实 | FK → games ON DELETE CASCADE；`id INTEGER PK AUTOINCREMENT` |
| `daily_summary` | **每日聚合（心跳累加产生）** | `UNIQUE(date, game_id)` |
| `settings` | 键值配置 | `key PK` |
| `game_catalog` | Notion 总表快照 | `page_id PK` |
| `deleted_archive` | 删除留底（审计） | 只增 |

> `feature/multi-backend-sync` 额外有 `sync_records` / `game_mappings` / `provider_configs` —— **main 上没有**。
> 位置：`SqliteRepository.InitializeDatabase()`（`:64`），`CREATE TABLE` 在 `:69-185`，10 条 `try{ALTER}catch{}` 在 `:190-266`，启动去重 `DeduplicateGamesAndDailySummaries` 在 `:287` 起。
> 连接串：WAL + `synchronous=NORMAL` + `foreign_keys=ON`；每次操作新建连接；写操作走全局 `SemaphoreSlim _writeLock`。

**`sessions` 真实列（`main`）**：
```
id INTEGER PK AUTOINCREMENT, game_id, pid, process_name,
start_time DATETIME, end_time DATETIME, last_heartbeat DATETIME,
duration_seconds INTEGER, is_active INTEGER, created_at DATETIME
```
→ **没有** `global_id` / `device_id` / `version` / `deleted_at` / 任何 UTC 列。

### 1.2 Session 生命周期

```
MonitorLoopAsync（5 秒，后台线程池 Task）
 ├─ CleanupZombieSessionsAsync()                     按 PID 判存活，死的结束会话
 ├─ Win32ProcessMonitor 扫描 → ProcessFilter 黑名单 → GameLibraryManager.DetectGame
 ├─ GetOrCreateGameAsync() → StartSessionAsync / HeartbeatSessionAsync
 │    └─ 心跳：delta = now - LastDailyFlushTime → FlushDurationToDailyAsync()
 │          └─ 按会计日 DailyCutoffHour（24~30）拆成两笔分别累加
 └─ 进程消失 → EndSessionAsync（同样处理跨日）
```
- **时长是心跳增量累加出来的**，不是"起止时间相减"。`sessions.duration_seconds` 存**绝对值**，`daily_summary` 存**累加值**。
- 心跳周期 = `ProcessScanIntervalSeconds` = **5 秒**（`SessionHeartbeatIntervalSeconds` 是死配置，全库无引用）。
- 多进程同游戏会**按 gameId 合并**，避免时长虚增。
- 崩溃/重启恢复：启动 `CleanupStaleSessionsAsync(3min)` → `GetActiveSessionsAsync` 恢复仍活跃的会话，`LastDailyFlushTime = LastHeartbeat`（**空档不补算**）。
- `tracker/` 的 Python 实现是遗留线，已冻结，与本方案无关。

### 1.3 Heartbeat 与会计日

- 5 秒心跳；结算点 `DailyCutoffHour` 支持 24~30（24 = 00:00，28 = 次日 04:00，避免深夜游戏跨日割裂）。
- 拆分实现在 `GameSessionManager` + `AccountingDateHelper.GetNextCutoffBoundary`。
- ⚠️ 现有 `sessions.start_time` 等是**本地时间字符串**（`"yyyy-MM-dd HH:mm:ss"`），只有 `created_at/updated_at` 用 SQLite `CURRENT_TIMESTAMP`（= UTC）。**多设备同步必须解决这个时间基问题**（见 §2.3）。

### 1.4 游戏 Mapping（现状很薄）

- `main` 上只有 `games.notion_page_id` **一列**，没有 provider 概念。
- 匹配逻辑在 `Core/Services/GameMatcher.cs`（identifier / exact / normalized 三级确定性匹配，模糊匹配已移除）。
- exe 路径相关列在 `games.executable` / `games.executable_path`（**设备本地信息，绝不能跨设备复用** —— 与规格 §16 一致 ✓）。

### 1.5 Notion 同步

- `Infrastructure/Notion/NotionServices.cs`（`NotionClient` + `NotionSyncService`，约 111KB）。
- 链路顺序（**不可颠倒**）：
  `RefreshGameCatalogCache → ReconcileNotionDeletions → AutoLink → Pull → BackfillRelations → SyncPendingDailyRecords → RefreshDailyTitlesFromMaster`
- 触发点：启动 / 游戏退出（延迟 500ms）/ 首页「立即同步」/ 窗口重新获得焦点（60s 节流）。**周期同步已取消**。
- `daily_summary.sync_status`：`pending` / `synced` / `unmapped`（终态）/ `error`。
- ⚠️ **Notion 读的是 `daily_summary`**（`GetPendingDailySummariesAsync`、`RefreshDailyTitlesFromMasterAsync`）。所以**任何对 `daily_summary` 的语义改动都会直接影响 Notion 同步**（重复推送 / 反复回刷的风险）。

### 1.6 后台服务生命周期与启动/退出

- `App.OnLaunched` → 单实例互斥（`Global\Sappfiler_SingleInstance_Mutex_...`）→ 注册全局异常 → `new MainWindow()`。
- `MainWindow` 构造函数里**装配全部服务**（repo / monitor / library / sessionManager / NotionClient / NotionSyncService / SyncOrchestrator / ArtworkService / ViewModels / 托盘）→ `_ = InitializeAndStartMonitoringAsync()`（fire-and-forget）→ `Task.Run(MonitorLoopAsync)`。
- 关窗口只 `Hide()`（**曾经隐藏时拆视觉树，因原生崩溃已整个删除，不要加回来**）。
- 托盘「退出」= `Environment.Exit(0)`：**不 Cancel `_monitorCts`、不 flush、不等同步**。
- 日志：`AppLog`（exe 目录 `data\logs\app.log`，2MB 轮转，保留 1 代）。

### 1.7 与规格一致的既有事实（好消息）

| 规格要求 | 现状 |
|---|---|
| §71 同步不得阻塞游戏监听 | 监听已在独立后台 Task，同步同样挂后台即可 ✓ |
| §46 crash recovery 不交给云端 | 现有恢复机制健全，只需在"恢复出会话"后补一个 UPDATE 同步 ✓ |
| §47 不要每秒同步 duration | 现有心跳只在本地滚动，天然符合 ✓ |
| §36 删除要 tombstone | 已有 `deleted_archive` 留底先例，思路一致（但语义需区分，见 §2.4） |
| §16 exe path 是设备本地信息 | `games.executable/_path` 现状就是本地语义 ✓ |
| §18 Notion Page ID 作远程身份 | `games.notion_page_id` 现状一致 ✓ |

## 2. 规格 vs 代码事实：7 个必须你拍板的分歧点

> 这一节是本文档最重要的部分。规格里有些要求**直接照做会破坏现有功能**，或需要改动"计时核心"。

### 2.1 【最大分歧】"不要同步 Daily Total" vs `daily_summary` 是心跳累加产物

- 规格 §9/§58/§79 要求：只同步 **Session 事实**，`Daily Total` / Heatmap / Ranking 全部本地重算。
- 但**现有 `daily_summary` 不是派生数据**：它是心跳**直接增量写入**的（`AddSessionDurationToDailyAsync`），`sessions` 只是同时存了绝对值。
- 而且 `daily_summary` 被 **Notion 同步链消费**（`sync_status` / `notion_page_id` / `notion_title` 快照都在上面）。

**若强行改成"由 sessions 重算 `daily_summary`"，会牵动**：`GameSessionManager` 全部写入路径、`GetPendingDailySummariesAsync`、标题回刷、统计口径 → 违反"不破坏现有功能"。

**我的建议（分阶段，Phase 1 零风险）**：
- **Phase 1–4：`daily_summary` 完全不动**，同步只处理 `sessions`（事实）+ 同步元数据表。
- **Phase 5 单独设计 `daily_summary` 的跨设备语义**，并在动手前给你一份"影响面 + 回滚方案"让你拍板。可选方向：
  - (A) 远端 sessions 应用后，**按日期重算 `daily_summary.duration_seconds`**（只统计非活跃会话的 sum），并把受影响行的 `sync_status` 重置为 `pending`（保证 Notion 会重推）；
  - (B) 每台设备只上报"自己产生的时长"，跨设备合并放到展示层（不改表语义，但"总数"要靠聚合）。
- **需要你确认**：接受"`daily_summary` 的跨设备统一延后到 Phase 5 单独决策"吗？

### 2.2 表名与主键：`game_sessions` + UUID PK vs 现有 `sessions` + INTEGER PK

- 规格 §7 要求 `game_sessions` 表、`session_id` 全局唯一。
- 现状：表名 `sessions`，主键 `id INTEGER PK AUTOINCREMENT`，`daily_summary.game_id` 等通过它做 FK（ON DELETE CASCADE）。

**建议**：**保留 `sessions` 表与 INTEGER 主键**，追加列：
```
global_id         TEXT     -- UUID，回填（真随机，绝不用 日期+游戏名+时长 派生）
device_id         TEXT     -- 产生该会话的设备 UUID；历史数据 = 当前设备
version           INTEGER  -- 每次本地修改 +1
deleted_at_utc    TEXT     -- tombstone（NULL = 未删）
started_at_utc    TEXT     -- 见 2.3
ended_at_utc      TEXT
```
+ `CREATE UNIQUE INDEX idx_sessions_global_id ON sessions(global_id)`。

**理由**：改主键要动 FK CASCADE、`DeduplicateGamesAndDailySummaries`、所有写入/查询路径 —— 违反"不重写 SQLite 层"。
**需要你确认**：接受"global_id 作为同步标识、INTEGER id 继续做本地内部键"吗？（这就是你规格 §5 里"本地可以保留 INTEGER 内部 ID"的写法）

### 2.3 时间基：规格要求核心时间 UTC，现状是本地时间串

**建议**：**新增** `started_at_utc` / `ended_at_utc` / `deleted_at_utc`（TEXT ISO-8601 UTC），**不改**现有 `start_time/end_time/last_heartbeat` 的语义与消费者（本地 UI/报表继续用）。
- 同步只走 UTC 列。
- 历史回填：用**回填时刻的系统时区**把历史本地串换算成 UTC。跨 DST 的历史数据无法 100% 精确还原 —— **历史回填允许近似**。
- **需要你确认**：接受"历史数据 UTC 回填按当前时区近似、且不追溯 DST"吗？

### 2.4 Tombstone：新增表 vs 复用 `deleted_archive`

- 已有 `deleted_archive`（`kind` / `source` / `reference` / `deleted_at`）是**审计留底**，语义是"我们删过什么"。
- 同步需要的 tombstone 语义是"**要告诉别的设备这条已删**"，且有 30 天保留 / 逐设备确认 / 不能立即物理清除的要求。

**建议**：**新增 `sync_tombstones`**（独立语义、独立生命周期），但**删除时两张表都写**（审计 + 同步），并在 HANDOVER 里写清两者区别。
**需要你确认**：接受"新增 `sync_tombstones`，不复用 `deleted_archive`"吗？

### 2.5 凭证存储：现状是明文，规格要求 DPAPI

- 规格 §41/§42 要求 WebDAV 密码与 Cloudflare Token 用 Windows Credential Manager 或 DPAPI，不明文进 SQLite —— **同意**。
- 但**现状恰好相反**：`settings.notion_token` 就是**明文存 SQLite**（另外 `config.json` 里也有一份明文 token，属 Python 遗留）。

**需要你确认两件事**：
1. 新同步凭证确认走 DPAPI（我按这个做）。
2. **旧 `notion_token` 是否一并改造**？（这会改动现有行为，影响"设置页保存/测试连接"路径；不做也能工作，只是明文风险留在原地）

### 2.6 `sync_queue` 的 payload 存什么

规格 §10 给了 `payload` 列。**建议只存"引用"而不存内容**：
```
queue_id, entity_type, entity_id(global_id), operation(CREATE/UPDATE/DELETE),
base_version, created_at_utc, retry_count, next_retry_at, status, last_error
```
真值在推送时**从业务表现读**（避免队列与业务表双写漂移；也让"合并多条变更"变得容易 —— 你规格 §68 的 debounce/batch 需求）。
**需要你确认**：接受"队列不存 payload 快照"吗？（若坚持存快照，需要额外一套"队列快照与业务表一致性"的保证逻辑，复杂度和出错面都更大。）

### 2.7 目录/命名（已在 §0.2 说明）

**需要你确认**：`DeviceSyncModels.cs` / `Infrastructure/DeviceSync/` / `ISyncBackend` / Provider-vs-Backend 术语规则。
另外：本分支的 remote mapping **直接采用 feature 已定的 `game_mappings` 形状**（含 `provider` 列）而不是另建 `remote_mappings`。

## 3. 我建议的数据库设计（Phase 1 产出，基于 main 的 6 表基线）

> 全部放在**新文件** `Infrastructure/Database/DeviceSyncSchema.cs`，由 `InitializeDatabase()` 调用一行。所有语句幂等（`CREATE TABLE IF NOT EXISTS` + `try{ALTER}catch{}`），可重入、失败不破坏现有数据。

```sql
-- 设备
devices(device_id TEXT PK, device_name TEXT, platform TEXT, app_version TEXT,
        created_at_utc TEXT, last_seen_at_utc TEXT, last_sync_at_utc TEXT,
        status TEXT DEFAULT 'active')            -- active | inactive | revoked

-- 设备本地的游戏映射（exe path 属于这里，绝不上云共享）
device_game_mappings(mapping_id TEXT PK, device_id TEXT, game_id INTEGER,
        process_name TEXT, exe_path TEXT, launcher TEXT, launcher_app_id TEXT,
        created_at_utc TEXT, updated_at_utc TEXT,
        UNIQUE(device_id, game_id, process_name))

-- 远端身份映射（★ 采用 feature 的 game_mappings 形状，避免两套表）
game_mappings(mapping_id TEXT PK, game_id INTEGER, provider TEXT,
        remote_id TEXT, remote_locator TEXT, remote_name TEXT,
        match_type TEXT, match_confidence REAL, last_verified_at_utc TEXT,
        created_at_utc TEXT, updated_at_utc TEXT, version INTEGER,
        UNIQUE(game_id, provider))

-- 变更队列（不存 payload 快照）
sync_queue(queue_id TEXT PK, entity_type TEXT, entity_id TEXT, operation TEXT,
        base_version INTEGER, created_at_utc TEXT, retry_count INTEGER DEFAULT 0,
        next_retry_at_utc TEXT, status TEXT DEFAULT 'pending', last_error TEXT)

-- 每个 backend 独立的游标与状态
sync_state(backend TEXT, account_id TEXT, cursor TEXT, last_success_at_utc TEXT,
        last_error TEXT, PRIMARY KEY(backend, account_id))

-- tombstone
sync_tombstones(entity_type TEXT, entity_id TEXT, device_id TEXT,
        deleted_at_utc TEXT, PRIMARY KEY(entity_type, entity_id))

-- sessions 追加列（见 §2.2 / §2.3）
ALTER TABLE sessions ADD COLUMN global_id TEXT;
```

## B.2 【已回答】daily_summary 是否属于本次事务？——是

从结束会话的真实路径读出来的事实（`GameSessionManager.cs:167-211` + `SqliteRepository.cs:765-901`）：

```
GameSessionManager.EndSessionAsync
 ├─ 1. FlushDurationToDailyAsync(...)      → daily_summary += 尾部增量（跨结算点则 2 笔，各自独立连接）
 ├─ 2. _repo.EndSessionAsync(...)          → sessions 落结束（自己的连接）
 │      └─ 内部还会**重算 daily_summary.session_count**（同一次调用里，第 3 次写库）
 └─ 3. SessionEnded 事件
```

**结论：属于同一事务。** 理由：
1. 这三笔写入在语义上是**同一个事件**（"这局结束了"）：尾部增量入账、有效场次重算、会话标结束。
2. 若把 `daily_summary` 留在事务外：崩溃会留下"会话已结束且已入 Outbox，但 `daily_summary` 少算尾部增量"→ 本地总量 ≠ 事实之和，而 Phase 5 对账**无法区分**这是"跨设备数据"还是"本地漏写"。
3. 若把 Outbox 留在事务外：就是用户第 16 条要防的"本地有、云上永远没有"。

**同时明确边界**：
- **心跳路径**（`HeartbeatSessionAsync` → `FlushDurationToDailyAsync`，每 5 秒）**保持原样**：只写 `daily_summary`，**不入队、不进新事务**（同步不参与运行中的会话）。
- 结束路径才做"尾部增量 + session_count 重算 + 会话结束 + Outbox 入队"的**单事务合并**。
- `EndSessionAsync`（仓储）里那段 "session_count 重算"（含 `substr(start_time,1,10)` 用**日历日**而非会计日的既有行为、`manualBonusSessions` 判定）必须**逐字复刻**，不得顺手"修正"——那是既有行为，改动会波及 Notion 同步。

## D.3 实施中发现的**第三个坑**（实测踩到，已修）

**症状**：`UNIQUE constraint failed: games.global_id` → 去重整组回滚 → 两个游戏**永远合并不了**（日志里只有一行 WARN，很难查）。

**原因**：冻结契约的顺序是 ④（canonical 继承 global_id）→ ⑤（删除重复行）。而 canonical 要继承的那个 identity，**此刻还挂在被合并行身上**（⑤ 还没执行）→ 唯一索引直接拒绝写入。

**修法**：在同一个事务内，先做一步"**摘除**"——把 identity 从即将被合并的行上置为 NULL，再交给 canonical：
```sql
UPDATE games SET global_id = NULL
WHERE id IN @dupIds AND NULLIF(TRIM(global_id), '') IS NOT NULL;
```
- 保持冻结的语句顺序（④→⑤）不变；
- 摘除只是把状态先归零，**任一步失败都会随事务回滚**，identity 不会真的丢；
- 顺带消除了"两行持有同一个 global_id"这种脏数据撞上唯一索引的可能。

**这条已写进代码注释**：顺序不是随便排的，改动前必须先看清。

## E.3 协议语义（逐条对应你冻结的要求）

**Push**：`Pending → InFlight → Backend ACK → Completed`
- **只有出现在服务端 accepted 列表里才算落库成功**；只认本批的 change_id（防后端脏数据）。
- **ACK 丢失**（服务端已落库、响应没回来）：客户端按失败处理 → 退回 Pending + 退避 → 重推
  **同一个 `change_id`**（= `outbox.queue_id`，重试中不变）→ 服务端幂等去重 → **不产生重复数据**。
- 既没 accepted 也没 rejected 的（**部分响应**）同样按失败退避 —— 绝不能当成"已完成"。
- 永久拒绝（云端已有墓碑）→ **死信 `Failed`**，不再无限重试。

**Pull**：`拉取 → 在本地 transaction 中应用 → 更新 cursor → COMMIT`
- **数据与游标在同一个事务**。若拆成"先推游标再写数据"，崩溃就是
  "云端已消费、本地没写"的**永久丢数据**；现在的语义是崩溃后重拉同一批，而落地按 `global_id` 幂等。
- 游标按 Backend 隔离。空拉取也记录服务端高水位。

**顺序**：`Push → Pull → 落地 → 推进游标`。注释里明确写了这是**当前默认循环策略，不是写死的协议约束**。

## E.4 落地规则（保守、刻意不做 LWW）

按顺序逐条判断，**跳过的一律计入 `Deferred` 并写日志**（不静默丢弃）：

|---|---|---|
| 远端 Delete | 写本地墓碑（幂等） | 墓碑传播 |
| 本地已有该 `global_id` 的墓碑 | 跳过 | **墓碑优先**，陈旧设备不能复活已删除实体 |
| 本地已有同 `global_id` 实体 | 跳过 | 不覆盖；重复 Pull 天然不产生重复实体 |
| 业务键（platform + platform_id）已被**另一个** identity 占用 | 跳过 | 这需要**身份对账**（2b 那套继承/墓碑规则），不是覆盖能解决的，**不猜** |
| Session 的游戏还没到本地 | 跳过 | `sessions.game_id NOT NULL`；推送顺序本身保证 Game 先于 Session |
| `schema_version` 不认识 / payload 坏了 | 跳过 | 宁可不同步，也不能解错 |

## G.1 用户冻结的硬约束（已逐条落代码）

事务内顺序（**不要随意调整**）：

```
BEGIN
  → 确保 game.global_id

  → 写 started_at_utc / ended_at_utc

  → 结束 session
  → 用事务内最终确定的数据生成 immutable payload 快照

```

| 约束 | 实现 |
|---|---|

| **payload 必须用事务内最终确定的数据** | ⚠️ 特意在 UPDATE 之后**从库里读回** session 与 game 的最终状态再生成 payload —— 任何"忘记同步某字段"都会在读取处暴露 |

## I.3 Identity Rule Engine（纯函数，可单测）

### 键优先级（用户裁定）

```
A. platform + platform_id      ← 强键
B. executable_path（归一化）    ← 弱键
C. executable（文件名）         ← 弱键
D. normalized name             ← 最终兜底，极保守
```

### 强键冲突阻断（用户修正 ①，核心）

> **强身份键出现明确冲突时，弱身份键不得跨越该冲突进行自动合并。**

形式化：

| 情形 | 行为 |
|---|---|
| A **适用且相等** | 合并（最高置信） |
| A **适用且不等** | **阻断 → Deferred**（不得再看 B/C/D） |
| A **不适用**（任一侧缺失 / 不可比） | 才允许落到 B |

用户给的典型场景（必须被阻断，不得因 B 相同而合并）：

```
远端: Steam / 123456   path = D:\Games\Foo\foo.exe
本地: Steam / 999999   path = D:\Games\Foo\foo.exe      ← A 冲突 → 阻断
```

**「A 适用」的判定**（复用项目里既有的启发式，保持一致）：
双方 `platform` 非空且相等、**且都不是 `manual`**、且 `platform_id` 均非空、
且**不疑似本地 id / GUID 形态**（长度 8 或 16 —— 与 `DeduplicateGamesAndDailySummaries`
评分里 `PlatformId.Length != 8 && != 16` 的既有判据一致）。
> 依据：`MainWindow` 在识别不到平台时会把 **本地行 id** 当 `platform_id` 写进去（`existing.Id.ToString()`），
> 那种 `platform_id` 跨设备毫无意义，绝不能被当成强键。

### B / C / D 的收紧（**我的补充，需你确认**）

- **B 相同** → 合并（前提：唯一命中）。
- **B 不同** → 落到 C（跨设备盘符/目录不同是正常的，**不阻断**）。
- **C 相同** → 仅当**唯一命中**时合并；多候选 → Deferred。
- **D 相同** → 极保守：仅当双方都**没有任何可用 A/B/C**、唯一命中、**且双方 Notion Page ID 不冲突**
  （即都未绑定，或绑定到同一个 page）时才合并；否则 Deferred。
  > 理由：双方绑定了**不同**的 Notion 页面却按名字合并，等于毁掉一个 Provider 身份 —— 与你关心的"不静默破坏身份"一致。

### 全局铁律

**任何自动合并都必须「唯一命中」**；只要存在多个候选 → **Deferred，绝不猜**（用户裁定）。

## I.4 `status = 'ignored'` 硬护栏（用户裁定：绝对优先）


`ignored` 是**本地用户意图，不是普通业务字段**：远端数据**不得**通过

## I.5 Game reconciliation（两种形态）

| 形态 | 场景 | 动作 |
|---|---|---|
| **形态 1：远端身份尚未落地** | 本地只有 AAA，远端 BBB 因为业务键冲突被 Deferred（BBB 从未插入本地） | ① 记录 supersession `(Game, BBB) → AAA`；② `resolution = redirected_to_canonical`。**不改本地任何行** |
| **形态 2：远端身份已落地成行** | 本地同时存在 AAA 与 BBB（BBB 之前同步进来过） | ① 把 BBB 行并入 AAA（sessions / daily_summary 迁移，口径复用 2b）；② 删除 BBB 本地行；③ 记录 supersession。**全程不写 tombstone** |

**两条铁律**：

1. **canonical 的 `global_id` 必须保留**（本机权威 identity 永不改写）。
2. ⚠️ **不得复用 `DeduplicateGamesAndDailySummaries` 的墓碑分支** —— 2b 的去重在丢弃重复行时会
   `WriteGameTombstone`，而 2e 的语义是"身份合并"而非"实体删除"。形态 2 只能复用它的
   **迁移部分**（sessions/daily 合并），**必须绕开它的墓碑写入**。

## I.6 Supersession 语义（用户修正 ②）

**语义定义**：

- `sync_tombstones` = **这个实体被删除了** → 对端收到后删除本地副本。
- `sync_identity_supersessions` = **这个身份等同于那个身份** → 对端收到后把引用**重定向**到 canonical，
  绝不删除数据。

**必须满足**：`合并身份` 与 `删除实体` **在数据模型和同步语义上严格区分**。

**本轮实现范围**：只在**本地**建立 `sync_identity_supersessions` 表与判定/写入逻辑。
**线上传输表示（新 `SyncEntityType` 或新 operation）不在 2e 范围内** —— 它属于集成阶段，
并在那时**必须**满足"不复用 `SyncOperation.Delete`"这条约束。本附录把该约束先记为硬性要求。

**本地重定向规则**（2e 内可立即生效）：应用远端变更时，若 `entity_global_id`（或其 `game_global_id`）
命中 `sync_identity_supersessions` → 解析为 canonical 后再继续（幂等，`resolution = redirected_to_canonical`）。

## I.7 Session reconciliation（用户裁定）

**「同一事实、不同身份」的判定（四项全部满足）**：

```
same device_id
+ same started_at_utc
+ same duration_seconds
+ same game identity        ← 用户补充的必要条件
```

> 加 game identity 的理由（用户原话）：否则存在理论上"同一设备、同一秒开始、同样 3600 秒、Game A / Game B"
> 被误判 —— **identity reconciliation 不应该依赖概率**。

**处理原则**：

| 情形 | 行为 |
|---|---|
| 同 `global_id` 已存在 | 幂等跳过（2c 已有） |
| 判定为同一 immutable fact | identity reconciliation：保留一条 + 记录 supersession，**不产生第二份 session** |
| 依赖的 Game 尚未落地 | Deferred（2c 已有；游戏就绪后 2e 可重处理） |
| 无法确认 | Deferred |

**明确不做**：`duration max` / LWW / 任何"取更大值"策略 ——
**Session duration 是事实，不是可合并属性**。
