## 第六轮：双向删除（用户抱怨"程序里删的和 Notion 里删的互不影响"）

用户拍板的语义：**删游戏 = Notion 每日记录 + 总表条目都删**；**Notion 里删了 → 本地物理删除**。

### 改动前的真实行为（取证）
1. `DeleteGameAsync` 只有一句 `DELETE FROM games`，本地 sessions/daily_summary 靠 FK CASCADE 消失；`INotionClient` 里**没有任何删除/归档方法**，删除完全不出网。
2. `QueryGameMasterAsync` / `QueryDailyRecordsAsync` 只做 upsert，从不判断"远端少了谁"，Notion 删页面后本地 `notion_page_id` 变悬空指针。
3. **单向复活**：`SyncDailyRecordFromNotionAsync` 在本地找不到游戏时会新建 `manual` 游戏行，所以本地删掉的游戏会被下一轮 Pull 造回来。

### 实现
- `NotionClient.ArchivePageAsync`：`PATCH /pages/{id}` + `{archived:true}`。Notion API 没有真删除，这是唯一方式（进回收站，30 天可恢复）。项目锁的是 Notion-Version 2022-06-28，字段名是 `archived`（新版 API 改叫 `in_trash`，别混）。
- `NotionSyncService.DeleteGameEverywhereAsync(gameId, deleteMasterEntry)` / `DeleteDailyRecordEverywhereAsync(id)`。
- `NotionSyncService.ReconcileNotionDeletionsAsync()`：远端没有的 page_id → 本地删。**两道安全阀**：① 远端集合为空则整段跳过（空结果通常意味着权限/网络异常）；② 本地只处理 `sync_status='synced'` 的行，pending/error 本来就可能还没进 Notion。
- `RefreshGameCatalogCacheAsync` 现在会在 upsert 之后**清掉不在本次拉取结果里的 catalog 行**，让 `game_catalog` 成为总表的忠实快照（顺带修掉了长期"只增不删"、假 page_id 残留的老问题）。
- 防复活：Pull 时跳过 `GameMasterPageId` 非空但不在 catalog 快照里的记录。
- 新增 `deleted_archive` 表：物理删除前留底（kind/source/reference/payload_json）。
- UI：删除前统一弹 `DeleteConfirmDialog`（原来**连确认都没有**，点一下就删）；确认框用红底"确认删除"+ 默认按钮为"取消"；历史页新增逐条删除入口（原来根本没有删每日记录的地方）。

### 验证
- xunit 新增 `NotionDeletionSyncTests` 10 个用例（自建 `FakeNotionClient`，覆盖：远端删记录对账、pending 不误删、空集安全阀、catalog 清理、总表条目消失则删游戏、防复活、删每日记录归档、删游戏归档全部+总表、不删总表选项、未配置 Notion 时跳过）。**52/52 通过**。

## 第七轮：用户反馈"在 Notion 每日表删掉 Vampire Survivors，没有影响到程序"

### 结论：功能本身是好的，差的是触发时机
真实库取证（用户已重启，`deleted_archive` 表已建，说明新构建跑过了）：
```
id=1 kind=daily source=notion ref=2026-09-17 热血江湖  at=18:51:33   ← 启动链的对账，删对了
id=2 kind=daily source=app    ref=2026-09-18 不思议迷宫 at=18:51:52   ← 用户点历史页新删除按钮
```

## 顺带挖出并修掉三个潜伏 bug（都是"Notion → 本地"导入链上的）

起因：同步状态显示"已从 Notion 同步 1 条记录"，但 Notion 每日表明明有 11 条。于是把 pull 的 `catch{}` 换成逐条打印异常，真凶立刻现形：

1. **`SyncDailyRecordFromNotionAsync` 建游戏行漏了 `executable_path`**（该列 `NOT NULL`）→ 整条 INSERT 报 `SQLite Error 19: NOT NULL constraint failed: games.executable_path`。11 条里 10 条失败。**这条路径从来没有工作过**，而调用方是空 `catch{}`，所以一直表现为"同步成功但数据没进来"。修法：两处 INSERT 都补 `executable_path`，并填 `''`（同时把 `executable` 也留空，这样「按 exe 注册手动游戏」的循环会跳过这些本地并不存在的游戏）。
2. **`identifiers_json` 用 Dapper 泛型读不到**：`QueryFirstOrDefaultAsync<NotionGameCatalogItem>` 无法把 JSON 文本列映射到 `List<string> Identifiers`（列名 `identifiers_json` 和属性名 `Identifiers` 对不上）→「游戏标识」永远空列表 → 导入的游戏只能用随机 8 位 id，和运行中检测到的同一款游戏（真实 AppID）对不上，会变成两条记录。修法：改成 `QueryFirstOrDefaultAsync<dynamic>` + 手工 JSON 反序列化（与 `GetCatalogItemsAsync` 一致）。
3. **pull 循环里的空 `catch{}`** 改成统计失败条数 + 记录首条错误，并拼进 `SyncStatusChanged` 文案，避免同类问题再被吞掉。
4. 顺带：未填「游戏标识」时，从封面 URL 提取 Steam AppID 来定 `platform_id`（`GameMatcher.ExtractSteamAppId`，本来就是为此写的）。真机数据上，Squeakross → `steam/2871440`、吸血鬼爬行者 → `steam/3265700`、风暴怕死队 → `steam/3561220` 都取到了真实 AppID。

修好 (1) 之后，用真实库副本复验：11 条记录**全部导入成功**，本地 games 从 4 → 11。也就是说用户重启后，Notion 里还留着的那些记录对应的游戏会被真正拉回本地。

**已知遗留（未修，需要把游戏解析挪到 sync service 才能用 matcher）**：没有 relation 的「未绑定」记录会按标题建 `manual` 游戏，而已绑定记录按总表名建，同一款游戏可能出现两个名字（如 `Pass the Fear` 与 `风暴怕死队`）。

## 12min 不更新根因：Pull 洗掉 pending（14:35，v1.0.8）
- QA 实测：本地 42min，Notion 停在 12min。日志链：13:51 创建成功（12min）→ 之后每轮"全部记录已是最新"+ Pull 恒"同步 1 条"。
- 根因：SyncDailyRecordFromNotionAsync 的 UPDATE 分支无条件 sync_status='synced'。心跳 AddSessionDurationToDaily 置 pending → 下一轮先 Pull 后 Push，Pull 又把 pending 洗掉 → Push 永远查不到待上传。时长用 Max 保留但状态被洗。400（13:40-13:47 的 Update 失败）让窗口期更长，但即使无 400 也会发生。
- 修复：Pull upsert 时若本地秒数 > 远端分钟 → 保留 pending（本地领先是事实源）；否则 synced。新增回归测试 Pull_KeepsPending_WhenLocalDurationIsAhead（60/60）。FakeNotionClient 加 UpdatedPages 记录 Update 调用。
- 遗留观察：Update 路径成功后 isBound=false 时置 "unmapped" 而非 synced（GetUnmappedDailySummariesAsync 会重推，行为待观察）；13:40-13:47 的 400 具体原因要等 v1.0.7+ 日志。
